# UX の原理

判断に迷ったときに戻る場所です。数値と食い違う場合は `ux-implementation.md` と `budgets.json` を優先します。数値は解釈の余地が小さく再現性が高いためです。

---

## 1. 人間中心設計の4原則

| 原則 | 内容 | 実装への帰結 |
|---|---|---|
| 根本原因を解く | 提示された問題は症状。答えが「人間のミス」になっても止めず、なぜ間違えられる状態だったかまで進む | 不具合をその画面の修正で終わらせず、同じ誤操作が他画面で起きうるなら共通部品を直す |
| 人に焦点を置く | 技術の能力ではなく人の必要と能力を起点にする | 設定項目を増やして判断を利用者へ転嫁していないか疑う |
| 活動中心のシステム視点 | 部品ではなく活動全体を支える。局所最適は全体を劣化させる | 画面単位のレビューで承認せず、連続した操作を通して確認する |
| 素早い試作と検証 | 短い試行を繰り返す。対象本人に試させ、考案者は観察者にとどまる | 実装後に5人へ触ってもらう |

## 2. 活動中心設計

第3原則の強調です。適用条件は「支えている活動を深く理解していること」で、これを欠くと失敗します。

| 主張 | 実装への帰結 |
|---|---|
| 自動車、時計、記譜法、楽器はHCDの審査を通らないが世界中が習得している。活動の理解が深く設計意図が伝わるため | 慣習から外れる判断は、活動の理解を根拠にできる場合のみ |
| 技術が人に合わせるのではなく、人が技術に適応してきた。道具が活動を定義する | 「直感的であるべき」を理由に学習を全否定しない |
| 個人に最適化するほど他者に合わなくなる。習熟すると必要な画面が変わる | 特定利用者像への過剰な最適化を避ける |
| 要望をそのまま実装すると肥大化し一貫性を失う。設計モデルに合わない要望は捨てる | 要望は概念モデルとの整合で判定する。合わないなら断るかモデルを更新する。両方しないまま追加するのが最悪 |
| 一貫した概念モデルを持つ強い設計判断が必要 | 一貫性の責任者を決める。全員の合意で決めると平均値に落ちる |

## 3. 伝達としてのデザイン

設計者と利用者の間には、設計者のモデル、システムイメージ、利用者のモデルの三者関係があります。設計者は製品を通してしか語れないため、伝達はすべてシステムイメージを経由します。

| 主張 | 実装への帰結 |
|---|---|
| 概念モデルは物語。文脈と理由を与える。物語がないと操作は暗記になり、想定外から回復できない | 情報構造がその作業の物語を反映しているか確認する |
| 人は説明を求める。情報が足りないと誤った説明を作る。誤解は無知より悪い | 空の状態を、何が起きるかと最初の一歩を説明する場所として使う |
| 選択肢を見せるだけでは足りず理由が必要。無効化されたメニューは理由も回復手順も伝えない | 無効化には必ず理由と回復手順を添える。理由のない `disabled` は禁止 |
| 概念モデルは正確でなくてよい。適切な行動を導ける程度に十分で、側面ごとに別モデルでよい | 完全な説明より、次の一手が分かる説明を優先する |

## 4. 感情と使いやすさ

| 状態 | 認知への影響 | 帰結 |
|---|---|---|
| 肯定的 | 幅優先で創造的だが気が散る。小さな困難に寛容になる | 落ち着いた場面では余白・活字・動きの質が実際の使いやすさを助ける。装飾ではなく機能への寄与 |
| 否定的 | 深さ優先で集中するが視野が狭まる。簡単な作業も難しくなる | 障害対応・決済・削除確認・締切直前の入力では装飾を削り、正しい操作を最も目立たせる |

魅力的なものはよく動きます。ただし表層だけの設計は否定されています。真に美しいものは有用に機能し、理解でき、使えるものです。

## 5. 人道中心設計

帰結: 数年後に負債化する箇所（データ構造、URL設計、権限モデル、外部連携）を短期の都合で決めない。偏りを持ち込む箇所（氏名欄、性別、住所形式、色だけの意味付け）を実装時に洗い出す。

## 6. 良いデザインの10原則

| 原則 | 実装への翻訳 |
|---|---|
| 革新的である | 技術の進展が機会を与える。革新それ自体を目的にしない |
| 実用的である | 実用性を最重視し、それを損なうものを排除する |
| 美しい | 毎日使うものは暮らしの質に影響する。ただし丁寧に仕上げたものだけが美しい |
| 分かりやすい | 構造を際立たせる。最良の場合は自己説明的になる |
| 主張しない | 道具であり装飾品ではない。利用者の自己表現の余白を残す。動きと装飾は理解を助ける場合のみ |
| 誠実である | 実際以上に見せない。守れない約束で操作しない。進捗の偽装、無意味な待機演出、成功に見せて後で失敗する実装は禁止 |
| ながもちする | 流行を避けるため古びない |
| 細部まで完璧 | あいまいさを残さない。細心さは利用者への敬意。状態網羅を完了条件にする |
| 環境にやさしい | 資源を節約し、物理的にも視覚的にも汚染しない |
| できるだけ少なく | 本質に集中する。画面に足す提案には何を減らすかを併記する |

## 7. ユーザビリティの定義

学習しやすさ、効率、記憶しやすさ、エラー（数・深刻さ・回復のしやすさ）、満足度の5要素で定義されます。これとは別に有用性（必要な機能があるか）があります。

```
役に立つこと = 有用性 + ユーザビリティ
```

同格です。欲しいものでなければ簡単でも意味がなく、できるはずでも操作できなければ意味がありません。

## 8. 10のユーザビリティヒューリスティック

| 項目 | 実装での確認 |
|---|---|
| 1. システム状態の可視化 | 結果を伴う操作を通知なしに実行しない。反応はできるだけ即時 |
| 2. 実世界との一致 | 画面上の語彙に内部用語（テーブル名、ステータス内部値、例外文言）が漏れていない |
| 3. 利用者の制御と自由 | 取り消しとやり直しを支える。中断手段を明示し見つけられる場所に置く |
| 4. 一貫性と標準 | 内部の一貫性と外部の慣習の両方を守る。利用者は他製品で過ごす時間のほうが長い |
| 5. エラーの予防 | 不注意による滑りには制約と良い既定値、思い違いには記憶負荷の除去と取り消しと警告。損害の大きい誤りから潰す |
| 6. 想起より認識 | 前の画面の情報を覚えている前提の画面を作らない |
| 7. 柔軟性と効率 | 繰り返す操作にキーボードからの到達手段を用意する |
| 8. 美的で最小限 | 平坦にするという意味ではない。要素が主要な目的を支えているかで判断する |
| 9. エラーからの回復 | 何が起きたか、なぜか、次に何をするかを平易な言葉で。エラーコードのみは禁止 |
| 10. ヘルプと説明 | 必要な瞬間に文脈内で出す。別ページへの誘導に頼らない |

## 9. 品質と作り込み

作り込みは品質を生む入力です。外部に委託しきれません。

| ルール | 内容 |
|---|---|
| 品質を判断基準にする | 「速く出せるか」ではなく「品質が上がるか」で判断する |
| 仕様は最低線 | 扉は開けば技術的には機能する。仕様を出発線として扱う |
| 品質は完璧さではない | 粗いものから磨いてよい。品質の基準を越える前に利用者へ見せない。実用最小限は社内利用に限る |
| 範囲を狭める | 品質が難しいと感じるのは手を広げすぎているから。全部を端まで詰められないなら一部だけを突出して良くする |
| 意見を持つ | 誰か特定の人のために設計してこそ優れる。全員向けの柔軟なものはどの用途でも優れない |
| 引き渡しをしない | 着想から完成まで関与し続ける。過度な分業は品質の縦割りを生む |
| 不具合を溜めない | 課題を短い期限で修正する方針を持つ |
| 産出は設計ではない | 設計の難所は形の生成ではなく、形とその文脈の良い適合を見つけること。生成された形を解決済みと取り違えない |
| 問題を先に設計する | 設計案件が長引く最大の理由は問題が不明確なこと。問題を1〜2文で書き、反応が出たら止めて合意を取る |
| 設計負債はまとめて返す | 実装の内部は見えないが体験は全体として見える。1画面だけ更新すると整合が崩れる。進化が速いなら2〜3年ごと |

## 10. 指針間の対立

指針が対立するときは、解消せず適用条件で分けます。

| 対立 | 分け方 |
|---|---|
| 「要望をそのまま実装すると破綻する。ときには無視するのが最も役に立つ」 と 「観察し反復する」 | 「何を言うか」は根拠にせず「何をするか」を根拠にする。観察は必ず行い、要望の直接実装は概念モデルとの整合で判定する |
| 「A/Bテストで決めない。直感を信じる」 と 「直感は経験に基づく判断か確認バイアスのいずれか」 | 判断根拠を言語化できるなら経験に基づく判断として採用する。できないなら確認バイアスとして扱い検証に回す |
| 「利用者は変化を嫌う。新鮮さのための再設計は悪化させる」 と 「設計負債は2〜3年ごとにまとめて返す」 | 理由が「新鮮に見せたい」なら行わない。積み上げで一貫した構造が失われているならまとめて返す |
| 「本文は16px以上」 と 「走査と入力が主目的の画面は基準14px」 | 用途で分ける。読み物と公開ページは16px、一覧と表と設定画面は14px。日本語の行間1.7前後は両者が一致するため変えない |
| 「携帯端末を起点に段階を上げる」 と 「机上ブラウザを基準幅とし狭い幅を上書きで足す」 | 既定は机上ブラウザ。要件に携帯端末が主要経路と明記された場合のみ切り替える。判断は `ux-implementation.md` 第3節 |
| 「良いデザインは目立たない」 と 「様式を決めないと無個性になる」（`visual-styles.md`） | 目立たせる対象で分ける。骨格と装飾は目立たせない。主題と主要操作は目立たせる。様式の選択は骨格の作り方の選択であり、装飾を足すことではない |
