# UX の実装規約

数値は `budgets.json`（プロジェクトでは `e2e/budgets.json`）が単一情報源です。変更するときはそのファイルだけを編集します。原理は `ux-principles.md` にあります。判断が食い違う場合はこの文書を優先します。

---

## 1. 時間

| 時間 | 意味 | 実装 |
|---|---|---|
| 0.1秒 | 自分が操作を起こしたと感じられる上限 | 開閉・選択・切替・並び替えは即時反映。サーバー応答を待たず楽観更新する |
| 1秒 | 遅延に気付くが思考の流れは保たれる上限 | 画面遷移は1秒以内。超えるなら押下時に先に反応を返す |
| 10秒 | 注意の限界。短期記憶が保てなくなる | 同期的に待たせず非同期化し、進捗と残り時間を示す |
| 1分 | 単純な作業を完了できるべき時間 | 主要な単一作業を1分で終える構成にする |
| 1分以内 | 送信確認や取引通知を返すべき時間 | 届かないと利用者は失敗を疑う |
| 1営業日以内 | 人手を介する問い合わせの応答上限 | 応答期限を明示する |

楽観更新は失敗時に必ず元へ戻し、失敗した事実を伝えます。

パフォーマンス予算（LCP / INP / CLS / 初期JS）は `budgets.json` の `webVitals` と `bundle` にあります。計測は対応ブラウザの実物と本番相当のビルドで行います。開発サーバーの数値は代替になりません。`scripts/verify.sh` と `assets/e2e-quality.spec.ts` が自動で判定します。

## 2. 状態網羅

正常系だけを実装した時点は未完成です。6状態すべてで完了とします。

| 状態 | 要件 |
|---|---|
| 読込中 | 押下に即時反応。レイアウトを確定させ表示後の変動を起こさない |
| 空 | 何が入る場所かと最初の一歩を示す。「データがありません」のみは不可 |
| 部分取得 | 取得できた分を表示し、失敗範囲を明示し、その範囲だけ再試行できる |
| エラー | 何が起きたか、なぜか、次に何をするかを平易な言葉で。エラーコードのみ不可。再試行を同じ場所に置く |
| 権限なし | 未認証と区別する。誰に依頼すれば使えるかを示す |
| 成功 | 完了を通知し、画面の状態にも反映する |

実装は `assets/ui-baseline.md` の判別共用体です。`switch` に既定節を置かないことで、状態追加時の実装漏れが型エラーになります。

## 3. 机上ブラウザ前提の構成

主入力はポインタとキーボードです。幅は `budgets.json` の `viewport` にあります。`designPx` が設計と検証の基準、`minSupportedPx` が横スクロールを出さないことを機械検査する下限、`reflowPx` が WCAG 2.2 AA SC 1.4.10 の要求する下限です。

携帯端末が主要経路になる製品では携帯端末起点の構成へ切り替えます。いずれの場合も「1画面に置く要素を減らす」は保持します。画面が広いことは要素を増やす理由になりません。

| 構成の規約 | 内容 |
|---|---|
| 分岐点は狭い側へ書く | 素の指定を基準幅向けとし、狭い幅は `max-*` 変種で上書きする。広い側へ足していく書き方では、どちらが基準か読めなくなる |
| 分岐点は内容で決める | 端末名や既製の幅ではなく、内容が壊れる幅で切る。部品単位の分岐にはコンテナクエリを使う |
| 縦積みを既定にしない | 主題と付随情報を縦に並べると基準幅で横が余る。横に並べてから、狭い側で積む |
| 縦積みへ落とす境界は最小対応幅に合わせる | 対応範囲内で複数のレイアウトを持つと、確認対象と基準画像が増える |
| 本文の行長を制限する | 幅いっぱいに流すと行末から行頭への戻りが失敗しやすくなる。読む内容には行長の上限を持たせ、走査する一覧には幅を使う |
| スクロールは縦だけ | 横スクロールは表や時系列など区画の内側に閉じる。画面全体が横に動く状態は不整合として扱う |
| ナビゲーションを常設してよい | 「内容が先、ナビゲーションが後」は幅の制約から出た規約であり、基準幅では当てはまらない |
| 「戻る」を自作しない | ブラウザが戻る手段を持つ。重複させるとどちらが何をするか分からない。階層を上がるなら別の語を使う |
| 行き止まりを作らない | 内容の末尾に次の移動先を置く。幅と無関係に成り立つ |
| 固定要素は上端に寄せる | 下端の固定は内容を覆い、拡大したときに占める割合が増える |

`<meta name="viewport" content="width=device-width">` を省略しません。省略するとブラウザが仮想の幅で描画し、拡大縮小の挙動も変わります。

ウィンドウは任意の寸法に変えられます。基準幅で作ったあと、次の2つを確認します。`minSupportedPx` で横スクロールが出ないことは `assets/e2e-quality.spec.ts` が自動判定します。`reflowPx` での折り返しは人手項目です。AA を宣言する場合は避けられない要求なので、狭い幅を設計対象から外しても「縦スクロールだけで内容が失われない」ことは満たします。

## 4. ポインタとキーボード

操作対象の寸法は `budgets.json` の `target` です。`minPx` が既定の下限で、密な一覧や表を組めるよう `wcagMinPx`（WCAG 2.2 AA SC 2.5.8 の絶対下限）と同値に揃えてあります。`gapPx` が隣接する対象の間隔、`touchMinPx` はタッチ対応を要件に含めた場合にのみ適用します。見た目は対象領域の50〜100%でよく、余白で確保します。

本文中のインラインリンクは行高に従うため下限の対象外です。SC 2.5.8 の除外規定に当たります。

頻繁に押す、誤りの結果が深刻、連続作業の一部、のいずれかなら下限より大きくします。破壊的な操作を主要操作の隣に並べません。押し間違いは距離で防ぎます。

| 規約 | 内容 |
|---|---|
| `:hover` と `:focus-visible` を別に定義する | 同じ見た目にするとキーボードで現在位置が分からない。`:focus` を未定義にするとブラウザが `:hover` を代用することがある |
| hover だけで開示しない | キーボードと支援技術から到達できない。常時表示にするか、押下で開くか、`:focus-within` でも開くようにする |
| 当たり判定を見た目と一致させる | 見た目より狭い判定と、見た目の外まで反応する判定はどちらも不整合 |
| 主要な操作にキーボード経路を用意する | 繰り返し使う操作は往復の回数で効率が決まる。単一キーの割り当ては入力欄にフォーカスがある間は無効にする |
| Tab の順序を視覚順に合わせる | `tabindex` に正の値を使わない。DOM の順序で解決する |
| 閉じ込めない | 対話窓は Escape で閉じられ、開く前の位置へフォーカスを戻す |

スワイプできそうに見えてできない不一致を作りません。これは入力経路が変わっても残ります。

## 5. フォームと入力

| 規約 | 理由 |
|---|---|
| ラベルは入力欄の上 | 視線が縦一列で済み、長いラベルにも対応でき、幅が変わっても崩れない |
| `placeholder` をラベルに使わない | 仕様上は補足のためのもの。入力開始で消えるため何を答えているか分からず見直せない |
| 補足説明は入力欄の下 | 入力を始める直前に読める位置。入力後の訂正時にも同じ場所にある |
| 用途に合う属性を指定する | `type` で最適なキーボードが出る。未対応環境では無視されるため指定しない理由がない |
| メール・パスワード・URL は自動大文字化と自動修正を無効化 | 意図しない変換を防ぐ。自動修正由来の末尾空白も除去する |
| 賢い既定値を置く | 空欄より大幅に速く入力できる |
| 入力補助は書式を先に見せ、途中で変えない | 入力途中で書式が現れたり後から変わる実装は混乱を招く |
| 選択メニューを見直す | 開く・探す・選ぶ・閉じるで4回触れる。選択肢2〜3個はラジオ、狭い範囲の数値は増減ボタン、日付は日付選択、選択肢が多いなら全画面一覧 |

属性の対応表は `assets/ui-baseline.md` にあります。

レイアウトは3分類です。連続した入力（登録・購入）は質問数を削ることが最も効きます。非連続の更新（プロフィール編集）は全項目を展開せず、触れた項目だけを別画面か対話窓で編集します。文脈内の入力（コメント）は単一欄をその場に置きます。対話窓では、入力欄と決定の操作を同時に見える範囲へ収めます。窓の内側でスクロールさせるなら、決定の操作は窓の枠に固定します。

登録フォームを最初に見せることは、獲得した利用者を失う地点です。段階的関与（登録を後回しにしてまず使わせる）を既定にします。外部の資格情報を使う、メールやカレンダーなど利用者が既にいる場所から入力を受ける、も同じ方向です。

## 6. 文章

分量は紙媒体の半分以下にします。

読み飛ばし前提で書きます。見出しを2〜3階層にし（走査と支援技術の到達を助ける）、気の利いた表現ではなくそこに何があるか分かる語にします。結論を先に置き、途中で読むのをやめても要点が伝わるようにします。長い流れは機械的にページ分割せず、話題ごとにまとめて相互参照させます。

ボタン、エラー、空状態、確認の文言も同じ規約に従います。

## 7. アクセシビリティ

デザインシステムが対応済みでも製品が対応済みになるわけではありません。採用側に残るのは、部品ごとの設定（属性・ラベルの関連付け・役割）、部品の組み合わせ（要素選択・欄の順序・読み上げ順）、独自部品の作成（最も難しい）の3つです。

完璧な対応は現実的ではなく、監査は数十から数百の項目を挙げます。優先順位を付けて「十分」の閾値を決めます。ただし対応は工程の1つではなく、発見から設計・実装・検証・運用まで貫く品質として扱います。

| 項目 | 基準 |
|---|---|
| コントラスト | `budgets.json` の `contrast`（文字 4.5:1 / 大きい文字と UI 部品 3:1。WCAG 2.2 AA）。`secondaryText` 3:1 のみ、段11の補足文字を淡く落として視覚階層を作るための意図的な緩和で AA を満たしません |
| 折り返し | `budgets.json` の `viewport.reflowPx` の幅で、二次元スクロールなしに内容と機能が失われない（SC 1.4.10） |
| 操作対象の寸法 | `budgets.json` の `target.wcagMinPx` を絶対下限とする（SC 2.5.8） |
| キーボード | すべての操作に到達でき閉じ込められない |
| フォーカス | 現在位置が常に分かる。`outline: none` の単独指定は禁止 |
| 色 | 状態・必須・エラーを色以外でも伝える |
| 画像 | 意味のある画像に代替テキスト、装飾は空の代替 |
| 見出し | 階層の順序を保つ |
| 動き | `prefers-reduced-motion` を尊重する |
| ラベル | `label` の `for` と入力欄の `id` を対応させる |
| テーマ | 明色・暗色・高コントラストの3テーマすべてで基準を満たす |

コントラストと3テーマの確認は `assets/e2e-quality.spec.ts` が自動判定します。生成式は測定の代わりになりません。

## 8. 日本語 UI

| 項目 | 規約 |
|---|---|
| IME | 確定前の入力で検索や検証を走らせない。`compositionstart` から `compositionend` の間は確定待ちとして扱う。`keydown` の `isComposing` を確認する |
| 文字数 | `String.length` は絵文字と結合文字で人の数え方と一致しない。表示する文字数は `Intl.Segmenter` の grapheme 単位で数える |
| 全角と半角 | 数値・電話番号・郵便番号は入力時に半角へ正規化する。検証で弾くより正規化するほうが摩擦が少ない |
| 氏名 | 姓名の分割を前提にしない。ミドルネームと単一名の利用者を弾かない。ふりがなを必須にする場合は理由を持つ |
| 禁則と折り返し | 見出しや短い文言は `word-break: auto-phrase`（未対応環境では通常の折り返し）または明示的な改行位置指定で不自然な分断を避ける |
| 行間 | 日本語は英字より字面が大きいため、英字向けの行間では詰まって見える。本文は 1.7 前後を既定にする |
| 数値の書式 | 桁区切りと通貨は `Intl.NumberFormat('ja-JP')` に任せる。手書きしない |
| 日付 | 和暦が要件にある場合のみ扱う。`Intl.DateTimeFormat` の `japanese` 暦を使い、自作しない |

## 9. AI を界面に載せるとき

入力と出力を構造化された形で管理すると認知の負荷が下がり、結果のばらつきも下がります。会話欄だけの界面にせず、従来の界面を持つ機能する応用を作り、そこへ AI の機能を補完として組み合わせます。

設計の問いは「どうすればこの人がこれを行えるように助けられるか（実行の隔たり）」から「どうすればこの人が、それがうまく行われたかを判断できるように助けられるか（評価の隔たり）」へ移ります。

| 規約 | 内容 |
|---|---|
| 会話欄を横に貼るだけにしない | 既存の課題そのものを作り替える。空状態から作らせる導入は、使える下書きを生成して編集させる形に変える。分類体系を覚えさせる絞り込みは自然言語の問いに変える。決められた欄に人が合わせる入力は、画像・PDF・URL を受けて構造化を機械側で行う形に変える |
| 出力の評価手段を必ず用意する | 生成物をそのまま採用させない。差分・根拠・確認・承認・取り消しのいずれかを備える |
| ループを可視化する | 行動・結果・フィードバック・修正の各段階が利用者から見える |
| 代理の作業範囲を明示する | 何をしてよいか、どこで人の承認を要するかを界面上で示す |
| 生成物と人の入力を区別する | どこまでが生成され、どこから人が確認したかを表示する |
| 生成された形を解決済みと扱わない | 生成された界面は仮説。適合の確認は別途行う |

## 10. 再設計の判断

作る側は同じ画面を数千時間見ており、利用者は年間数時間しか見ていません。作る側が感じる「古さ」は利用者の感覚と一致しません。慣れた設計は好まれます。利用者は設計を鑑賞しておらず、作業と自分のデータに注意を向けています。頻繁に使う人ほど習熟した操作に依存するため変更を嫌います。

既定は、最初に正しく作り、その後は緩やかに変えることです。大きく変える判断が正当化されるのは、現在の利用者がほとんどおらず大きな改善で利用者を大幅に増やせる見込みがある場合、または積み上げの結果として全体の一貫した構造が失われている場合です。

「新鮮に見せたい」は理由になりません。一方で破綻を放置し続けることも選択肢ではありません。設計負債は小刻みに増え、まとまった単位で返すのが現実的です。実装の内部構造は利用者に見えませんが、体験は全体として目に見えます。どの経路を通るかは予測できないため、一部の画面だけを更新すると全体の整合が崩れます。

## 11. 情報設計とページ構成

この節は公開ページ（紹介、着地、採用、催事）を作る場合にのみ適用します。認証後の業務画面には適用しません。業務画面の構成は `design-system.md` のドメイン設計に従います。

### 11-1. 順序を決める

情報設計は、何をどの順番で見せるかを決めることです。並べる順序が違うだけで、同じ内容が伝わったり伝わらなかったりします。

読み手は「これは自分に関係があるか」を最初に判定し、関係があると分かってから詳細を読みます。したがって、詳細より先に価値を置きます。

紹介ページで機能する典型的な順序です。案件に合わせて増減させますが、価値より先に価格や機能一覧を置かない点は変えません。

| 順 | 区画 | 果たす役割 |
|---|---|---|
| 1 | 主題 | 何のためのものかを一言で伝える |
| 2 | 課題 | 読み手が抱えている困りごとに触れる |
| 3 | 解決 | それがどう解消されるかを示す |
| 4 | 特徴 | 他とどう違うかを3つ前後に絞って説明する |
| 5 | 手順 | 使い始めるまでの流れを3段階前後で示す |
| 6 | 実績 | 判断を支える事実を置く |
| 7 | 価格 | 判断材料を提示する |
| 8 | 疑問 | 残った不安を解消する |
| 9 | 行動 | 取ってほしい行動へ導く |

### 11-2. 順序の失敗

次のいずれかに当てはまる構成は作り直します。

- 何のためのものか分かる前に、機能一覧や価格が出てくる
- 主要な行動への導線が画面のどこにあるか分からない
- 同じ内容が言い換えられて繰り返し出てくる
- 読み手の困りごとに触れず、提供側の言いたいことだけが並んでいる
- 主題の区画に情報を詰め込みすぎて、何が主題か読めない

### 11-3. 主題の区画

最初に目に入る区画です。ここで伝わらなければ、以降は読まれません。

含めるものは、見出し、補足の一文、主要操作、内容が伝わる図版の4つです。それ以外は置きません。見出しは `--fs-hero`、補足は `--fs-lg` 以下にして寸法差で階層を作ります。

主要操作はこの区画に1つだけ置きます。同じ画面の下部に再掲するのは構いませんが、いずれも塗りは1箇所です。

### 11-4. 行動への導線

取ってほしい行動を1つに絞り、語を統一します。同じ行動を指す語が画面内で揺れると、別のものだと受け取られます。

行動を促す区画は、判断材料（実績、価格、疑問への回答）を提示したあとに置きます。判断材料の前に置いた導線は無視されます。

導線の文言は、何が起きるかが分かる語にします。「送信」「次へ」のような一般語ではなく、「無料で試す」「資料を受け取る」のように結果を書きます。

## 12. 不自然な表示

規約を満たしていても、実際の製品では見かけない形になることがあります。多くは、説明責任を果たそうとして情報を足しすぎた結果です。次の形を作りません。

### 12-1. 補助テキストの置きすぎ

| 作らない形 | なぜ不自然か | 代わりに |
|---|---|---|
| 操作できるボタンの下に説明文を常時表示する | 実際の製品にこの形はありません。操作できるボタンは文言だけで意味が伝わる状態が正しい形です | ボタンの文言を、何が起きるか分かる語にします。それで足りないなら操作の設計を見直します |
| すべての入力欄に補足説明を付ける | 説明が並ぶと、本当に説明が要る欄が埋もれます | 補足は、形式の制約があるか、入力内容が結果に影響する欄にだけ付けます |
| ラベルと同じ内容を補足にも書く | 二重に読ませることになります | どちらかを消します |
| 画面上部に使い方の説明文を置く | 読まずに操作されます | 操作の場所に必要な情報を寄せます |
| 空でない状態にも「ここに一覧が表示されます」と併記する | 見えているものを説明しています | 空状態のときだけ出します |

無効化の理由は例外です。操作できない理由は表示する必要があります。ただし常時表示ではなく、無効化されている間だけです。置き場所は `assets/ui-baseline.md` 第3節の表で選びます。

### 12-2. 状態表示の不自然さ

| 作らない形 | なぜ不自然か | 代わりに |
|---|---|---|
| 一瞬で終わる処理に読込中の表示を出す | ちらついて壊れて見えます | `budgets.json` の `response.directManipulationMs` を下回る処理では出しません |
| 成功のたびに通知を出す | 通知が意味を持たなくなります | 画面の状態に反映されていれば通知は不要です。取り消しが必要な操作にだけ出します |
| 誤りの表示を画面上部にまとめる | どの欄が誤りか分かりません | 誤りは対象の欄の直下に置きます。件数の要約を上部に置くのは併用としてなら可です |
| 読込中に配置が動く | 表示後に押す場所が変わります | 寸法を保った骨組みを出します |

### 12-3. 導線と文言の不自然さ

| 作らない形 | なぜ不自然か | 代わりに |
|---|---|---|
| 同じ画面に同じ行動のボタンを3箇所以上置く | 押し忘れを心配しているように見えます | 主題の区画と、判断材料のあとの2箇所までにします |
| 操作の文言が画面ごとに揺れる | 別の機能だと受け取られます | 同じ行動は同じ語にします |
| 取り消せる操作に確認を挟む | 手数だけが増えます | 取り消しを用意して確認を省きます。確認は取り消せない操作にだけ挟みます |
| 「クリック」「タップ」と入力装置を書く | 装置が変わると誤りになります | 「選ぶ」「開く」のように行為で書きます |
| 「〜することができます」で説明する | 冗長です | 「〜できます」にします |
