# デザインシステム

---

## 1. Atomic Design の5段階

| 段階 | 内容 |
|---|---|
| Atoms | それ以上分解すると機能しない最小単位。ラベル、入力欄、ボタン。色や活字の定義も含む |
| Molecules | 原子を組み合わせた単純な部品。ラベル＋入力欄＋ボタンで検索フォーム。単一責務を守るための段階 |
| Organisms | 分子・原子・他の有機体を組み合わせた、界面の独立した区画 |
| Templates | 部品を配置に組み込み、内容の下敷きとなる構造を表現する。最終の内容ではなく内容の構造を扱う |
| Pages | テンプレートに実データを流し込んだ具体例。設計が実際の内容に耐えるかを検証する場所 |

Pages は変種を明示する場所です。買い物かご1件と10件、見出し40文字と340文字、権限のある人と無い人。これを扱わないと最良の場合だけを想定した壊れやすい実装になります。

## 2. ディレクトリへの適用

層名をディレクトリ名として採用します。

Next.js App Router:

```
src/shared/components/{atoms,molecules,organisms,templates}/
src/features/[domain]/components/
├─ server/                     Atomic の Templates と Pages の橋渡し
└─ client/{molecules,organisms}/[Name]/   Container / Presenter / Hook / テスト / index.ts
src/app/**/page.tsx            Atomic の Pages。実データを流し込む唯一の場所
```

TanStack Router / Start:

```
src/shared/components/{atoms,molecules,organisms,templates}/
src/features/[domain]/components/{molecules,organisms}/
src/routes/[route]/-components/Page.tsx   Atomic の Pages
```

### 層の判断

上から順に評価し、最初に一致した行を採用します。

| 順 | 条件 | 置き場所 |
|---|---|---|
| 1 | それ以上分解すると機能しない最小単位 | `shared/components/atoms/` |
| 2 | ドメイン語彙を含まず、複数ドメインで使える単純な組み合わせ | `shared/components/molecules/` |
| 3 | ドメイン語彙を含まず、界面の独立した区画 | `shared/components/organisms/` |
| 4 | 配置の骨格のみを持ち、実データを持たない | `shared/components/templates/` |
| 5 | ドメイン語彙を含み、単純な組み合わせ | `features/[domain]/components/molecules/` |
| 6 | ドメイン語彙を含み、界面の区画 | `features/[domain]/components/organisms/` |

atoms をドメイン側に作りません。ドメイン固有の最小単位が必要なら、まず既存 atom に variant を足せないかを検討します。

判断に15分を超えたら `features/[domain]/components/organisms/` に置き、共有され始めた時点で移します。判断に時間を使うより移動する前提で置くほうが安価です。

## 3. インターフェース棚卸し

既存の界面を持つプロジェクトでは、整備より先に棚卸しを行います。目的は3つです。統一されていない状態を可視化すること、共通の語彙を確立すること、作業範囲を把握すること。

手順とカテゴリ一覧は `assets/interface-inventory.md` にあります。すべての出現箇所ではなく、異なる表現を1つずつ取得し、残す部品、捨てる部品、統合できる部品、確定する名称、次の手順を決めます。

## 4. 境界

システムが所有するのは界面に関わる範囲だけです。ブランド、内容規約、声と口調、写真の指針、技術標準、人物像は、システムの傘の下で定義しません。界面に関わる範囲でのみ受け取ります。

## 5. 層構造

| 層 | 内容 | 必須か | このプロジェクトでの担当 |
|---|---|---|---|
| 中核 | 組織全体で共通の部品、トークン、アイコン | 必須 | `shared/` |
| 技術別 | 特定フレームワーク向けの薄い包み | 任意 | 使わない |
| レシピ | 特定の製品や製品群で一貫して使う組み合わせ | 任意 | `features/[domain]/components/` |
| 賢い部品 | 業務ロジックや通信を包んだ、そのまま使える部品 | 任意 | `features/[domain]/hooks/` |
| 製品 | 実際に出荷する画面 | 必須 | `app/` または `routes/` |

必要が生じてから層を足します。最初から複雑に設計しません。

中核は材料を提供し、製品側がその材料で組み合わせを作ります。よく使われているレシピは中核へ昇格させられます。

単発の部品はシステムに入れません。同じような単発の部品が5箇所で作られていたら、中核が共通の必要を満たしていない信号です。

## 6. 入れるかの判断

| 問い | 判断 |
|---|---|
| 1. 他の製品に関係するか | 自分の製品だけなら不足。もう1つなら会話の余地。3つなら共同体と議論。5つならおそらく入る |
| 2. システムの方針と整合するか | 既にある系列に加わるなら適合。方針に反する技術を持ち込むのは不適合 |
| 3. 作成と維持の費用は | 日付選択部品は多くの製品が使うが多くが独自版を必要とする。全員に合わせて誰にも合わないものを避ける |
| 4. 新しい方向への勢いを生むか | ツールチップは重なり順・影・位置合わせ・ポップオーバー・メニューへ波及する。全体に有用な方向を選ぶ |
| 5. どこまで使い方を導けるか | いつ使うか、どう設定するか、内容をどう変えられるか。語れないならまだ広く配る段階にない |
| 6. 時期は合っているか | システム側に空きがあるか。提案者に完了させる時間があるか |

完成した状態で持ち込まれる貢献はまずありません。残る仕事は、最小限の機能範囲まで広げること、合意が取れない機能を削って適用範囲を広げること、システムの構成と品質へ揃えることの3つです。

過剰設計の兆候は次の言葉です。現実が必要としている範囲まで戻します。

```
第3のボタン様式が必要になるかもしれないから先に作っておこう。
誰かが必要とするかもしれないからこのトークンも足しておこう。
```

品質の低いものを入れません。近道・応急処置・実験・急ぎの仕事は、システムには置き場所がありません。

## 7. トークン

3層で構成します。原始値（`blue-500`）、意味（`--foreground`）、部品固有（`button-primary-bg`）。部品層と分けて管理する理由は、テーマ切り替えを可能にすること、ブランド言語と部品の関心を分離すること、独立して更新できるようにすることです。

部品固有トークンを作りすぎないことが最重要です。部品と変種の掛け算で増え、すぐ管理不能になります。5000個を超えて全部品と全変種を網羅していた例があります。部品固有はテーマ間で大きく変わる強くブランド付けされた要素に限ります。命名で凝りすぎず先へ進めます。

実装は `assets/ui-baseline.md` にあります。

## 8. 視覚的な破壊的変更

コードの API には基準が共有されていますが、色・活字・余白は曖昧なまま運用されがちです。次を破壊的変更として扱います。

| 分類 | 破壊的とみなす変更 |
|---|---|
| 色 | 利用側の背景の上に載る文字色。利用側の文字が載る背景色。隣接要素との対比に関わる境界色や影 |
| 活字 | 折り返しや切り詰めを引き起こす字送り・字間・太さ・字面。密度の高い界面では特に危険 |
| 余白と寸法 | 部品の境界の外に出る余白（`margin`）、および隣接要素の配置に影響する寸法 |
| 重なりと透明度 | 複数部品で共有される重なり順、覆いの透明度 |

部品の内側に閉じた余白の調整は破壊的ではありません。原則として部品の境界の外側に余白を書きません。外側の余白は利用側が決めます。

活字は最初の安定版までに十分検討し、以降は安定を保ちます。危険な変更は次の大きな版へ回し、それまでは影響範囲が閉じた追加で対応します。

`assets/e2e-quality.spec.ts` の視覚回帰が、この分類の変更を機械的に検出します。

## 9. 運用

部品が見つからない、9割は合うが1割合わない、疑問がある。この3つが起きたときに何をすればよいかを明示します。明示されていないと利用側は独自の回避策を作り、システムは陳腐化します。

手順の骨格は、製品側がまずシステムで作る、見つからなければ相談する（会話で既存の解に導けることが多い）、単発かシステムの一部かを決める、初期案を作り両者で確認する、システム側が設計と実装と検証を行う、最終確認して文書化し版を上げて配布する、製品側が取り込み検証する、です。この手順はシステムが存在する前から決められます。

部品の検証観点は、内容（長い文字列・多言語・想定外の分量）、アクセシビリティ、ブラウザと端末、可変幅、機能、極端な場合（通常・境界・過酷の3種）、コード規約、設計言語との整合、実製品での試用です。

支援の受け付けは経路を絞り、応答期限を明示します。

## 10. 命名

名前は使われ方を規定します。文脈と内容に依存しない名前ほど再利用範囲が広がります。

| 避ける | 採用する | 理由 |
|---|---|---|
| `HomepageCarousel` | `Carousel` | 置ける場所が名前で制限される |
| `ProductCard` | `Card` | 入れられる内容が名前で制限される |
| `AdminSidebar` | `Sidebar` | 利用者の種別で制限される |

名前を決めるときは内側の内容を隠して構造だけを見ます。ただしドメイン層では意図的に文脈へ縛るため、ドメイン語彙を含む名前を使います。

## 11. 設計と実装の関係

コードが真実です。設計ツール側のライブラリは、コードで使えるものについての契約です。順序が逆になると、約束されたものが存在しない状態が生まれます。設計を先行させて数か月分の差を作ることは最も費用のかかる失敗です。

設計ツールで表現できない要素があります。動き、対話、可変幅の挙動、要素の順序、ボックスモデル、性能、利用者の環境設定、実際の文字の描画、ブラウザと端末の癖。これらはすべて設計の対象です。
